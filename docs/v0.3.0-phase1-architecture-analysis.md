# Prompt Jury v0.3.0 Phase 1 Architecture Analysis

Status: Complete  
Baseline: Prompt Jury v0.2.8  
Scope: Code analysis only; no Judge Core or Web Judge implementation

## 1. Executive summary

The current codebase can support the v0.3.0 Judge Engine as an incremental change. No large-scale refactor is required.

The enhancement specification assumes that the baseline has no Judge Engine, but v0.2.8 already contains a working OpenAI-compatible API Judge, blind candidate anonymization, weighted scoring, result persistence, and three synthesis modes. These capabilities should be adapted behind the new provider interface rather than reimplemented.

The genuinely new architectural work is:

1. introduce a provider-neutral Judge Core;
2. wrap the existing API Judge as the first `JudgeProvider`;
3. add Web Judge session lifecycle management, beginning with ChatGPT Temporary Chat;
4. allow multiple Judge runs per Evaluation Run without losing v0.2.8 history;
5. add Judge provider selection to the existing Side Panel.

## 2. Current runtime architecture

```text
Side Panel (React state, no router)
  │
  │ chrome.runtime.sendMessage
  ▼
Background Service Worker
  │  discovers tabs, injects content scripts, routes messages
  │
  │ chrome.tabs.sendMessage
  ▼
Platform Content Script
  │
  ▼
WebLLMAdapter
  ├── ChatGPTAdapter
  ├── GeminiAdapter
  ├── KimiAdapter
  └── DoubaoAdapter
       │
       ▼
NormalizedResponse
       │
       ▼
Side Panel → IndexedDB
```

The current API Judge runs directly in the Side Panel extension context:

```text
EvaluationBundle
  → anonymizeResponses
  → buildJudgePrompt
  → fetch(OpenAI-compatible API)
  → parse + Zod validation
  → weighted scoring
  → saveRunBundle
```

## 3. Provider architecture

### Current implementation

- `src/adapters/types.ts` defines the shared `WebLLMAdapter` interface.
- `src/adapters/registry.ts` owns a fixed registry of four adapter instances.
- `ChatGPTAdapter` contains site-specific DOM logic.
- Gemini, Kimi, and Doubao use `DomAdapterBase` with isolated selector configuration.
- Every adapter supports page detection, prompt entry, submission, completion polling, and extraction into `NormalizedResponse`.
- Adapter calls are stateful per content-script instance: each adapter records answer snapshots before sending so it can identify the new response.

### Reuse decision

Keep `WebLLMAdapter` unchanged for normal response collection. A Judge provider is not another response provider: it also owns session creation, cleanup, prompt construction, parsing, and Judge result validation.

Web Judge implementations may compose a `WebLLMAdapter`, but must not add Temporary Chat methods to the existing adapter interface. This avoids breaking the four current providers and keeps session policy outside DOM extraction.

### Required extension point

Phase 2 should introduce a separate `JudgeProvider` interface under `src/judge/core/`. Web implementations can use a session manager plus existing adapter behavior:

```text
WebJudgeProvider
  ├── JudgeSessionManager (create/close/leave)
  ├── existing WebLLMAdapter behavior (send/wait/extract)
  └── Judge parser/schema
```

## 4. Message system

### Current implementation

`src/messaging/schemas.ts` uses a Zod discriminated union for every cross-context request and response. The active routes are:

- `DETECT_PROVIDERS`;
- `PING_CONTENT`;
- `MOCK_ROUNDTRIP`;
- `SEND_PROMPT`;
- their corresponding content-script messages.

The Background Service Worker:

- queries all tabs and chooses the best matching tab per provider;
- retries content-script communication after programmatic injection;
- isolates failures per tab/provider;
- does not currently create or close conversation tabs;
- does not manage Judge sessions.

The content handler performs one linear operation for `CONTENT_SEND_PROMPT`: snapshot, set prompt, submit, wait, and extract.

### Required extension point

Do not overload `SEND_PROMPT` with Judge semantics. Later phases should add explicit, schema-validated messages for Web Judge lifecycle operations. The initial ChatGPT path will need operations equivalent to:

- create/open a temporary Judge session;
- run a Judge prompt in a specified tab;
- return extracted raw Judge output;
- close or leave the temporary session;
- report a stable, user-facing error code.

Session cleanup belongs in the Background/session layer because content scripts cannot close tabs and should not own browser-level lifecycle.

## 5. Storage

### Current implementation

IndexedDB database `multi-llm-response-lab` is at schema version 4 and contains:

| Store                | Purpose                              | Cardinality per run      |
| -------------------- | ------------------------------------ | ------------------------ |
| `evaluationRuns`     | Prompt and provider execution status | one                      |
| `responses`          | Normalized LLM responses             | many                     |
| `judgeResults`       | v0.2.8 API Judge result              | one (unique `by-run-id`) |
| `synthesizedAnswers` | Generated synthesis variants         | many                     |
| `runs`               | legacy compatibility store           | legacy                   |

`saveRunBundle` rewrites all responses and synthesized answers for a run and replaces its single Judge result in one transaction.

The existing `StoredJudgeResult` includes the Judge model, blind mapping, raw output, parsed result, and timestamp. `SynthesizedAnswer` is already richer than the v0.3.0 specification because it records the synthesis mode and allows multiple results.

### Migration decision

Preserve every existing object store and record. Phase 2/3 storage work should use an additive IndexedDB migration (version 5 or later):

- add `judgeRuns` with a non-unique `by-run-id` index;
- retain `judgeResults` for reading v0.2.8 data;
- migrate or expose legacy results through a compatibility reader without deleting them;
- reuse `synthesizedAnswers` rather than introduce a duplicate `synthesisResults` store unless a later requirement needs provider metadata;
- stop replacing all Judge history when a new Judge provider is run.

API keys remain in `chrome.storage.local` and must never be copied into IndexedDB, Judge results, errors, logs, or exports.

## 6. UI and routing

### Current implementation

There is no UI Router. `src/sidepanel/App.tsx` is a single React component with local state:

- `view` switches between `run` and `history`;
- the current `EvaluationBundle` drives response, Judge, and synthesis sections;
- Judge configuration opens the extension Options page;
- the Judge is currently hard-wired to the API implementation;
- the UI is bilingual through `src/i18n.ts`.

### Integration decision

Do not introduce a routing library in v0.3.0. Add a small Judge provider-selection state and components under the existing run view. Extracting Judge UI sections into focused components is acceptable, but rewriting the entire Side Panel is outside scope.

The existing flow must remain valid:

```text
collect responses → optionally run Judge → optionally synthesize → history/export
```

Provider selection should be inserted only between response collection and Judge execution.

## 8. Schema compatibility findings

The v0.2.8 schema is richer than the proposed v0.3.0 example and uses different field names:

| Specification             | Existing schema                                 |
| ------------------------- | ----------------------------------------------- |
| `ranking[].score`         | `ranking[].overallScore` plus `confidence`      |
| `evaluations[].risks`     | `evaluations[].riskFlags` with `type`           |
| `disagreements[].details` | `positions[]` plus `judgeAssessment`            |
| `recommendedAnswer`       | `recommendedAnswerId`                           |
| no summary/missing points | `summary`, `missingPoints`, `unsupportedClaims` |

The canonical internal result should retain the existing richer representation. The new Judge Core can normalize provider output into that schema. Replacing it with the smaller example schema would lose data, break stored v0.2.8 Judge results, and force unnecessary UI/export changes.

## 9. Error handling findings

Current strengths:

- adapter errors have stable codes;
- provider failures do not interrupt other response providers;
- API parsing distinguishes HTTP, empty body, invalid JSON, missing content, and SSE issues;
- API Judge and synthesis retry once.

Gaps for v0.3.0:

- API errors are still largely raw English strings and may expose provider response bodies;
- no explicit fetch timeout or abort controller exists for Judge API requests;
- Web Judge session errors and cleanup errors do not exist yet;
- Background routing currently collapses many failures into `ROUTING_ERROR`;
- provider-specific DOM/session errors need mapping to bilingual user-facing messages.

Phase 2 should define typed Judge error codes. API secrets and authorization headers must never enter error payloads.

## 10. Phase 2 implementation boundary

Phase 2 should add only provider-neutral core and tests:

```text
src/judge/core/judge-types.ts
src/judge/core/judge-engine.ts
src/judge/core/judge-runner.ts
src/judge/providers/mock/mock-judge-provider.ts
src/judge/schema/judge-result-schema.ts (or a compatibility export)
```

Recommended responsibilities:

- `judge-types.ts`: `JudgeInput`, `JudgeProvider`, provider metadata, typed errors;
- `judge-engine.ts`: provider registration, lookup, availability, and mode validation;
- `judge-runner.ts`: orchestration, blind input preparation, result normalization, timing;
- Mock provider: deterministic evaluation for tests without network or browser tabs;
- schema layer: preserve the current rich `JudgeResult` and export a single canonical validator.

Phase 2 must not yet:

- change existing Web adapters;
- add API network behavior;
- create browser tabs;
- migrate IndexedDB;
- change the Side Panel workflow.

## 11. Risks and controls

| Risk                                | Control                                                          |
| ----------------------------------- | ---------------------------------------------------------------- |
| Chat UI DOM changes                 | Keep selectors inside platform adapters/providers                |
| Temporary session pollutes history  | Default to temporary session and always attempt cleanup          |
| Closing the user's own tab          | Tag session ownership and close only tabs created by Prompt Jury |
| Existing history becomes unreadable | Additive DB migration and compatibility readers                  |
| API Judge behavior regresses        | Wrap existing client before changing it                          |
| Candidate prompt injection          | Preserve blind mapping and data-only Judge prompt rules          |
| API key leakage                     | Keep configuration separate; redact errors; test exports         |
| Edge blocks Gemini scripts          | Keep documented limitation; do not block ChatGPT Web Judge       |
| Monolithic UI grows further         | Extract only Judge-focused components, without adding a router   |
